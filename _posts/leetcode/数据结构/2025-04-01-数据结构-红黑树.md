## 2-3查找树
AVL树是一种完美平衡的树，不过维护平衡的代价太高，且读写不稳定，频繁读写的工程应用使用AVL的代价太高。

为了降低维护平衡的高代价，2-3搜索树诞生了，2-3树为了保持灵活性，允许一个结点最多保存2个键，2个键的结点能再指向**3**个结点。

一个结点中只有一个键，并且只有左右**2个**指出去的链接成为「2-结点」（「2-node」）；

一个结点中有两个键，并且有**3个**指出去的链接成为「3-结点」（「2-node」）；

2-3树的结点可以是「2-结点」，也可以是「3-结点」。

记忆2、3结点时，把2和3记忆成该结点有多少个儿子结点，「2-结点」就有左右两个儿子结点，「3-结点」就有左中右三个儿子结点。

叶子结点指向的链接被称为「空链接」（null-link）。

一个完美平衡的2-3查找树中的所有空链接到根结点的距离都是相同的，正是因为有「3-结点」，2-3查找树可以保证整颗树的这一特性。如何保证所有空链接到根距离的相同能在插入部分中找到答案。

### 查找
查找过程与二叉树大概是一致的。只是涉及到「3-结点」时可能需要中间的链接。

### 插入
考虑插入的各种情况，主要分为：向「2-结点」中插入新键，因为「2-结点」可以继续向「3-结点」演化，所以插入时不论父结点是啥都无所谓。

但向「3-结点」插入新键时，必然是会分解的，为了维护整颗树的平衡性，所以「3-结点」只会向父结点以上影响，希望将插入结点对整颗树的平衡影响传递给父结点以上的「2-结点」来吸纳变化，如果传到根结点时都没有「2-结点」吸收，那么根结点就会向上扩展高度+1，演化出一个「2-结点」。所以向「3-结点」插入时就分成了三种情况变化：没有父结点（自身就是根结点）、父结点为「2-结点」（父结点吸纳插入的影响）、父结点为「3-结点」（父结点继续向上传递影响）

#### 向「2-结点」中插入新键：
无论父结点是「2-结点」还是「3-结点」都无所谓，因为「2-结点」可以向「3-结点」演化，不会影响父结点。

#### 向一颗没有父结点的「3-结点」的树中插入新键：
为了将新键S插入，我们先临时将新键存入该结点中，使之成为一个「4-结点」，然后将「4-结点」分解为一个「2-结点」。

#### 向一个父结点为「2-结点」的「3-结点」中插入新键
当没有父结点时，「3-结点」插入新键就是上一个例子的情况，但是父结点为「2-结点」的时候，插入新键时的「4-结点」分解会影响到父结点。由于整个「3-结点」是大于父结点的，所以「3-结点」分解时，**中间键**可以融合到父结点形成一个新的「3-结点」，同时左键能在形成的「3-结点」中间链接下面，继续维持平衡。

#### 向一个父结点为「3-结点」的「3-结点」中插入新键
父结点为「3-结点」时，可以将这个过程看成两步，第一步是插入新键暂时形成的「4-结点」的分解，分解影响到了作为「3-结点」的父结点，中间结点的上移再次将父结点形成一个暂时的「4-结点」，第二步就是这个变成「4-结点」父结点的继续分解，过程就是跟一步类似的了，如果父结点的父结点还是「3-结点」，那就继续向上分解，如果父结点的父结点是一个「2-结点」，那分解过程就是跟上述第二种情况「向一个父结点为「2-结点」的「3-结点」中插入新键」类似了。

父结点的父结点还是「3-结点」，这在实际中的2-3树是不存在的，因为在向父结点为「3-结点」的「3-结点」插入新键时，就会改变父结点促使其分解，所以不会存在父结点的父结点还是「3-结点」。当然在局部讨论中，是可以这样归纳的进行讨论的。

### 全局性质
插入时，遇到了「2-结点」就自身消化插入键，不会影响树的高度；遇到了「3-结点」，就将新键带来的影响向父结点以上传递，或是父结点消化新键带来的「4-结点」影响，或是根结点分解为「2-结点」造成整体的树高+1，都保证了所有空链接到根结点的高度是相同的。此外，插入的影响都是消化在局部的，插入新键带来的影响始终保持在自身结点、父结点、父结点的父结点的范围内，不会影响到整颗树的有序性和平衡性。

结点的删除我们还没有讨论，但可以预见的是只有当删除结点会影响到整体2-3树的平衡时，叶子结点的父结点会进行旋转来保持新的平衡。

### 时间复杂度
时间复杂度：

在一棵大小为N的2-3树中，查找和插入操作访问的结点不超过logN个

其实这里我们已经可以看出2-3树的插入算法是非常稳定的，插入只需要进行局部变化，只涉及到相关的结点，不会影响树的全局有序性和平衡性，比起AVL的双旋转造成的影响，2-3树的影响非常小。

但是实现2-3树的编码难度却比较大，需要处理的情况太多：维护两种不同类型的结点，将被查找的键和结点中的每个键进行比较，将链接和其他信息从一种结点复制到另一种结点，将结点从一种数据类型转换到另一种数据类型。这些实现不需要大量的复杂的代码，它们产生的额外的开销可能会使算法比标准的二叉查找树更慢，代码也是更难维护和迁移的。

因此我们需要一种抽象来简化需要实现的代码，这种抽象就是大名鼎鼎的红黑树，红黑树本质上就是一棵2-3树的实现。下面我们将看到2-3树是如何抽象成一棵红黑树的。

## 2-3-4查找树
「2-3-4」查找树跟「2-3」树的区别只是增加了「4-结点」的存在，「4-结点」则是允许一个结点有三个键、四个儿子结点。

## 经典红黑树
经典红黑树的本质是一颗「2-3-4」树，只是在结点上附属上颜色信息来区分「2-结点」、「3-结点」、「4-结点」，「2-结点」用普通的黑链接表示，「3-结点」用一条红色链接链接的两个「2-结点」来表示，「4-结点」用两条红色链接链接的2个「2-结点」表示。之所以用颜色来表示「2-3-4」中的结点信息，主要还是考虑到「2-3-4」的代码实现，用二叉查找树来实现是非常有利于应对变化、简化代码、理解代码、维护代码等的。

实际实现红黑树时，我们是将红色链接的信息转移到结点上，

对于「3-结点」，我们规定子结点为红、父结点为黑；

对于「4-结点」，我们规定左右子结点为红、父结点为黑；

「3-结点」和「4-结点」的定义决定了红黑树中不允许有两个连续的红结点、红黑树中红结点的两个子结点都是黑结点。

红黑树的完整定义：

1. 红黑树的结点为红色或者为黑色；
2. 根结点是黑色的；
3. 每个叶子结点是黑色的；
4. 如果一个结点是红色的，则它的两个子结点都是黑色的；
5. 完美黑平衡：任意叶子结点到根结点经历过的黑结点数是相同的。

```java
static final class Entry<K,V> {
   K key;
   V value;
   Entry<K, V> left;
   Entry<K, V> right;
   Entry<K, V> parent;
   boolean color  = BLACK;
   Entry(K key, V value, Entry<K, V> parent) {
     this.key = key;
     this.value = value;
     this.parent = parent;
   }
   public boolean equals(Object o) {
     if(!(o instanceof Entry)) {
       return false;
     }
     Entry<?, ?> e = (Entry<?, ?>) o;
     return valEquals(key, e.getKey()) && valEquals(value, e.getValue())
   }
   public int hashCode() {
     int keyHash = (key == null ? 0 : key.hashCode());
     int valueHash = (value == null ? 0 : value.hashCode());
     return keyHash ^ valueHash;
   }
 }
 
 static final boolean valEquals(Object o1, Object o2) {
   return (o1 == null ? o2 == null : o1.equals(o2)); 
 }
```

#### 代码实现
```java
// 插入新键后，红黑树的调整操作
 private void fixAfterInsertion(Entry<K, V> x) {
   // 
   x.color = RED;
   while (x != null && x != root && x.parent.color == RED) {
     // 插入结点的父结点 为 左子结点。当插入「3-结点」时，意味着需要先 左旋
     if(parentOf(x) == leftOf(parentOf(parentOf(x)))) {
       // 父结点的亲兄弟结点
       Entry<K,V> y = rightOf(parentOf(parentOf(x)));
       // 父结点的亲兄弟结点为红色，说明插入的是一个「4-结点」
       if(colorOf(y) == RED) {
         // 反转颜色
         setColor(parentOf(x), BLACK);
         setColor(y, BLACK);
         setColor(parentOf(parentOf(x)), RED);
         // 继续迭代递归
         x = parentOf(parentOf(x));
       } else { 
       // 父结点的亲兄弟结点为黑色，说明插入的是一个「3-结点」
         // 插入结点在父结点的右侧时，需要先进行左旋
         if (x == rightOf(parentOf(x))) { 
           x = parentOf(x);
           rotateLeft(x);
         } 
         setColor(parentOf(x), BLACK);
         setColor(parentOf(parentOf(x)), RED);
         rotateRight(parentOf(parentOf(x)));
       }
     } else {
     // 插入结点的父结点 为 右子结点。当插入「3-结点」时，意味着需要先 右旋
       // 父结点的亲兄弟结点
       Entry<K,V> y = leftOf(parentOf(parentOf(x)));
       if(colorOf(y) == RED) {
         // 父结点的亲兄弟结点为红色，说明插入的是一个「4-结点」，需要反转「4-结点」的颜色
         setColor(parentOf(x), BLACK);
         setColor(y, BLACK);
         setColor(parentOf(parentOf(x)), RED);
         x = parentOf(parentOf(x));
       } else {
         // 父结点的亲兄弟结点为黑色，说明插入的是一个「3-结点」，需要反转「4-结点」的颜色 
         if(x == leftOf(parentOf(x))) {
           x = parentOf(x);
           rotateRight(x);
         }
         setColor(parentOf(x), BLACK);
         setColor(parentOf(parentOf(x)), RED);
         rotateLeft(parentOf(parentOf(x)));
       }
       
     }
   }
   root.color = BLACK;
 }
 private static <K,V> Entry<K,V> parentOf(Entry<K,V> p) {
   return (p == null ? null: p.parent);
 }
 /** 以p为旋转的最父结点，右旋转：父结点「p」的左子结点「l」的右子结点「l.right」变成「p」的左子结点「p.left」，l替代父结点p成新的父结点*/
 private void rotateRight(Entry<K,V> p) {
   if(parent == null) {
     return ;
   }
   // 左子结点
   Entry<K,V> l = p.left;
   // 父结点的左子结点 变为 左子结点的右结点 
   p.left = l.right;
   // 左子结点的右结点不为空时，将其父结点改为p
   if(l.right != null) {
     l.right.parent = p;
   }
   // 左子结点的父结点改为p的父结点
   l.parent = p.parent;
   // p的父结点的子结点重新指向左子结点l
   if(p.parent == null) {
     root = l;
   } else if(p.parent.right == p) {
     p.parent.right = l;
   } else {
     p.parent.left = l;
   }
   
   // 左子结点l的右子结点指向p，p的父结点指向l，完成右旋转
   l.right = p;
   p.parent = l;
 }
 private void rotateLeft(Entry<K,V> p) {
   if(parent == null) {
     return ;
   }
   // 
   Entry<K,V> r = p.right;
   p.right = r.left;
   if(r.left != null) {
     r.left.parent = p;
   }
   r.parent = p.parent;
   if(p.parent == null) {
     root = r;
   } else if(p.parent.right == p) {
     p.parent.right = r;
   } else {
     p.parent.left = r;
   }
   r.left = p;
   p.parent = r;
 }
```

```java
private transient Entry<K,V> root;
 /** The number of entries in the tree*/
 private transient int size = 0;
 public V put(K key, V value) {
   Entry<K,V> t = root;
   // 如果根结点为空，则创建一个根结点
   if(t == null) {
     compare(key, key);
     root = new Entry<>(key, value, null);
     size = 1;
     return null;
   }
   int cmp; 
   Entry<K,V> parent;
   while(t != null) {
     parent = t;
     cmp = key.compareTo(t.key);
     if(cmp < 0) {
       t = t.left;
     } else if(cmp > 0) {
       t = t.right;
     } else {
       // 如果该key已经存在，则修改其值，然后直接返回
       return t.setValue(value);
     }
   }
   // 如果没有匹配到该key，则表明要新增该key
   Entry<K,V> e = new Entry<>(key, value, parent);
   
   if(cmp < 0) {
     // 如果该key插入到是左边
     parent.left = e;
   } else {
     // 如果该key插入的是右边
     parent.right = e;
   }
   // 
   fixAfterInsertion(e);
   size++;
   return null;
 }
```

### 删除
删除的思想与BST的hibbard删除法一样，在删除结点x后用它的后继结点来填补它的位置。具体操作就是用后继结点的键值替换删除的结点x，然后删除这个后继结点。因此2-3-4树删除key的情形：

1. 删除的key不在叶子结点中时，用key的后继键值替换key，然后删除后继键值；
2. 删除的key在叶子结点：

由于后继键值一定是在「2-3-4」树的叶子结点上，所以最终要删除的键值始终都是在叶子结点。如果该叶子结点是「3-结点」或者「4-结点」，删除键值x不会影响树的平衡，可以直接删除，但如果该叶子结点是「2-结点」，删除后就无法保证完美黑平衡，因此需要**调整**后再做删除，始终保证树的平衡。

上面说的叶子结点是针对「2-3-4」树的，映射到红黑树就是：

删除的键在「2-3-4」中和红黑树

1. 删除的键在「2-3-4」树中的叶子结点：
    1. 叶子结点为「4-结点」，删除的键对应：
        1. 红黑树中的红结点：直接删除，不会影响平衡
        2. 红黑树中的黑结点：此时有两个红色子结点，用该黑结点的后继结点「右子红结点」替换，并删除后继结点。
            1. 代码上实际可以再判断这个后继结点。
    2. 叶子结点为「3-结点」：
        1. 红黑树中的红结点：直接删除
        2. 红黑树中的黑结点：此时一定会有一个红子结点，用红色子结点替换并置为黑色
    3. 叶子结点为「2-结点」：删除后需要做调整。
2. 删除的键不在叶子结点，用后继键值替换，并删除后继键值，后继键值一定是在「2-3-4」树中的叶子结点上。对应可能的情况为：
    1. 后继键值在「4-结点」中，必为红黑树中的红色结点，直接删除
    2. 后继键值在「3-结点」中：
        1. 如果是右斜「3-结点」，删除的键必定是黑色结点，删除黑色结点，用红色子结点替换并置为黑色；
        2. 如果是左斜「3-结点」，删除的键必定为红色结点，直接删除，不影响平衡。
    3. 后继键值在「2-结点」上，删除后需要做调整。

我们讨论了「2-3-4」中的情况，其实可以按照「2-3-4」树对应的情况来判断：在叶子结点或是不在叶子结点，但实际上代码上是红黑树结构，要判断是否是「2-3-4」的叶子结点，需要判断子结点的方向、颜色和数量来确定叶子结点是什么结点，还是比较复杂的。所以经典红黑树的代码是将所有的情况归纳为红黑树中的删除结点情形，故在上面的「2-3-4」树和红黑树删除的对应关系中，1-1-2 删除「4-结点」中的黑色结点就得转化为

## 左倾红黑树
可视化网站：[https://codetube.vn/visual/redblacktree/](https://codetube.vn/visual/redblacktree/)

我们讨论的红黑树是Left-Leaning Red-Black Trees，LLRB左倾红黑树。

红黑二叉查找树背后的基本思想是用标准的二叉查找树（完全由「2-结点」构成）和一些额外的信息（替换「3-结点」）来表示2-3树。

2-3树中的「2-结点」的普通链接用**黑链接**表示，「3-结点」则用一条**左斜**的红色链接（两个2-结点其中之一是另一个的左子结点）连接的两个「2-结点」表示。这样拆解成「2-结点」可以直接使用标准二叉查找树的查找算法。

红黑树的另一种定义：

1. 红链接均为左链接；
2. 没有任何一个结点同时和两条红链接相连；
3. 该树是完美黑平衡的，即任意空链接到根结点的路径上的黑链接数量相同。

第1点：红链接代表什么？为什么红链接都是左链接？

第2点很好理解，两条红链接相连就是「4-结点」了，「4-结点」在2-3树中是需要分解的；第3点也好理解，红链接链接的结点其实就是代表「3-结点」，如果把红链接放平，其实就是一棵「2-3树」，所以任意空链接到根结点的路径上的黑链接数量自然是相等的。

问题1: 红黑树每次插入为什么都是红色的链接？

因为红黑树本质上是2-3树，2-3树的插入就首先是在查找出来最近的一个结点中插入（原因是能保证插入后仍然保持平衡）。如：

如果插入之前结点是2-结点，插入后就变成3-结点，3-结点在2-3树中是满足的，所以不需要进行任何旋转分裂变化。由于是3-结点，所以链接就自然是红色的。

如果插入之前的结点已经是3-结点，插入后变成4-结点，此时4-结点则是需要分解的，所以红黑树中对应就是插入时链接也是红色的，但是两个红色表明是4-结点，所以需要分解。2-3树中的临时4-结点分解后还是能保证平衡的。

### 结点定义
红黑树是标准的二叉查找树，我们该如何定义红链接呢？首先红链接链接了两个结点，由一个结点指向另一个结点，如果两个结点中我们都用一个color变量来表示的话，这样会在两个「3-结点」链接时，红黑树中4个结点都是红色，这样其实会很难以区分「3结点」中两个结点的关系；因此用一个color变量来表示「3-结点」就足够了，至于是「3-结点中」的左结点（红黑树中的子结点）还是右结点（红黑树中的父结点）变红，肯定是由左结点表示比较好，因为二叉树中子结点会链接更多的结点。

### 插入
#### 向单个「2-结点」中插入新键
在「2-3树」中，如果是向单个「2-结点」中插入新键，是不会影响父结点的，同时不需要再进行任何多余的变换。「2-结点」变成「3-结点」，红黑树的定义中，插入结点的颜色会变成红色，除此之外，如果是在右链接中插入的，需要进行左旋转，来满足红黑树定义中的第一点：红链接均为左链接，但事实上，这个定义并不是绝对的，在「算法4」中的这个红黑树定义能够最大程度降低代码的复杂度，所以在这个定义下，我们进行「左旋转」也是无伤大雅的。

向树底部的「2-结点」插入新键

#### 向一个「3-结点」中插入新键
在「2-3树」中，我们考虑了向一「3-结点」中插入新键时父结点的三种情况，但在这里，我们先不用理会这个「3-结点」的父结点的情况。

插入新键，就会形成一个暂时的「4-结点」，红黑树中的中间结点就接了两个连续的红链接，就违反了红黑树的第2条定义：「没有任何一个结点同时和两条红链接相连」。因此这个暂时的「4-结点」就必须向父结点影响：「4-结点」的中间结点插入父结点。在红黑树中就等价于，父结点指向这个「中间结点」的链接颜色变为红链接，等价于此中间结点的颜色就由黑色变为红色。

插入新键有三种情况，新键的值处于「3-结点」中的最小值、中间值、最大值。如下图：

1. 如果插入新键c是最大值，插入位置就位于右链接；
    1. 此时该「4-结点」的中间结点为b，b插入父结点 == b成为红结点；
    2. a、c变为「2-结点」，a、c变为黑结点；
2. 如果插入新键b是中间值，插入位置就位于左结点的左链接；
    1. 中间值不跟父结点相连，同时产生两条连续的红链接，则进行右旋转
    2. 此时该「4-结点」的中间结点为b，b插入父结点 == b成为红结点；
    3. a、c变为「2-结点」，a、c变为黑结点；
3. 如果插入新键a是最小值，插入位置就位于左结点的右链接
    1. 中间值不跟父结点相连，红链接为右链接，则先进行左旋转，
    2. 此时该「4-结点」的中间结点为b，b插入父结点 == b成为红结点；
    3. a、c变为「2-结点」，a、c变为黑结点；

貌似插入新键是中间值和最小值时都必须先进行旋转，按理说如果按照「2-3」树和红黑树的定义，这个旋转其实没有解决什么问题。但事实上，右旋转和左旋转都保证了最后是中间键跟父结点相连（从上图中能清楚的看出），我认为这更多的是分解步骤的进一步细化的抽象，毕竟如果没有左旋右旋，将中间值插入父结点也是可以做到的，但是三种情况如何插入则需要分别讨论，这在写代码时无疑是麻烦的。所以不论什么情况，在拆解「4-结点」的时候将中间键的结点转化为与父结点相连是非常棒的抽象。

#### 插入的代码实现：
```java
public class RedBlackBST<> {
   private Node root;
   
   private void put(Key key, Value val) {
     root = put(root, key, val);
     // 根结点总是黑色，颜色变换可能会使根结点变为红色，
     root.color = BLACK;
   }
   
   private Node put(Node h, Key key, Value val) {
     if (null == h) {
       // 插入时，就标记为红结点
       return new Node(key, val, 1, RED);
     }
     int cmp = key.compareTo(h.key);
     if(cmp < 0) {
       h.left = put(h.left, key ,val);
     } else if(cmp > 0) {
       h.right = put(h.right, key, val);
     } else {
       h.val = val;
     }
     h = balance(h);
     return h;
   }
 }
 private Node balance(Node h) {
   // 左结点是黑色、右结点是红色，则进行左旋转；红色右链接的「3-结点」、连续红色链接的右结点
   if(!isRed(h.left) && isRed(h.right)) {
     h = rotateLeft(h);
   } 
   // 左结点是红色、左结点的左结点是红色，则进行右旋转
   if(isRed(h.left) && isRed(h.left.left)) {
     h = rotateRight(h);
   } 
   // 左结点、右结点都是红色，则进行颜色变换
   if(isRed(h.right) && isRed(h.left)) {
     filpColors(h);
   } 
   // 该结点下的总结点个数（包括自己）
   h.totalNodeCount = 1 + size(h.left) + size(h.right);
   return h;
 }
```

除了递归调用后中的三条if语句，红黑树中的put递归实现与二叉查找树中的put实现完全相同。他们在查找路径上保证了红黑树和「2-3」树的一一对应关系，使得树的平衡下接近完美。

第一条if语句会将任意含有红色右链接的「3-结点」（或临时的「4-结点」）向左旋转；

第二条if语句会将临时的「4-结点」中两条连续红链接中的上层链接向右旋转；

第三条if语句会进行颜色变换并将红链接在树中向上传递。

我们可以一瞅红黑树插入的详细过程：

### 删除
红黑树的删除操作比较复杂，红黑树本质上就是一颗「2-3」树，因此我们要从「2-3」树的角度上思考。

#### 删除最小键
最小键肯定是位于树底的叶子结点处，我们先讨论一下特殊的情况：

1. 红黑树只有根结点，此时无论根结点是「2-结点」还是「3-结点」，我们只需要删除即可。
2. 最小键是一个「3-结点」，此时只需要直接删除最小键即可，「3-结点」变成「2-结点」，红黑树的性质不变。

但更为普遍的是，最小键不在根结点，甚至可能在一个「2-结点」上，此时如果直接删除，会破坏红黑树的平衡特性，为了不破坏平衡，一个思路就是将这个「2-结点」变成一个非「2-结点」，那样我们就能放心大胆的删除。

最小键肯定是在最左子树中的， 我们在沿着左链接向下进行查找的过程中，我们会将我们遇到的所有「2-结点」变成「3-结点」或者临时的「4-结点」，不止是变换最底层的叶子结点，原因自然是再向上变换时考虑的情况会更复杂，代码更难写。沿着左链接向下变换到最底部后，再直接删除这个非「2-结点」的最小键，最小键被删除的同时也没有破坏平衡特性，但是因为向下变换的过程中可能产生临时的「4-结点」，因此我们还需要再向上将「4-结点」给分解掉。「4-结点」的分解插入的时候就已经有模版了，相对简单。

##### 沿着左链接向下变换
在向下将「2-结点」变换为「3-结点」和临时的「4-结点」时，从根结点开始，如果只有根结点，则只需要删除最小键。

1. 沿着左链接查找，如果左子结点是「3-结点」，继续向下寻找
2. 沿着左链接查找，如果左子结点是「2-结点」，
    1. 且父结点就是根结点时：
        1. 此时如果亲兄弟结点也是「2-结点」：左子结点合并父结点和亲兄弟结点，形成一个暂时的「4-结点」，树的高度减1；
        2. 亲兄弟结点不是「2-结点」：进行左旋转，亲兄弟的最小键转给父结点，父结点的最小键转给左子结点形成一个「3-结点」
    2. 父结点不是根结点时，此时父结点一定不是「2-结点」
        1. 如果亲兄弟结点也是「2-结点」，父结点中最小的一个键和亲兄弟结点转进左子结点，变成一个「4-结点」，
        2. 如果亲兄弟结点不是「2-结点」，进行左旋转，亲兄弟的最小键转给父结点，父结点的最小键转给左子结点形成一个「3-结点」

```java
/**
    * Removes the smallest key and associated value from the symbol table.
    *
    * @throws NoSuchElementException if the symbol table is empty
    */
 public void deleteMin() {
   if (isEmpty()) {
     throw new NoSuchElementException("BST underflow");
   }
 
   // if both children of root are black, set root to red
   // 递归的过程中要保证父结点一定不为「2-结点」，因此根结点要设置为红色，可能是为了减少代码
   // 这个设置貌似没有任何意义，如果这里设置为红结点，最后其实就没有必要再赋值根结点为黑结点；如果这里没有设置为红结点，最后赋值黑结点就是必须的，因为这样才能满足左倾红黑树的定义
   if (!isRed(root.left) && !isRed(root.right)) {
     root.color = RED;
   }
 
   root = deleteMin(root);
   if (!isEmpty()) {
     root.color = BLACK;
   }
   assert check();
 }
 
 // delete the key-value pair with the minimum key rooted at h
 private Node deleteMin(Node h) {
   if (h.left == null) {
     return null;
   }
   // 判断左子结点是否为「2-结点」：不是「2-结点」则继续往下找左子结点，是「2-结点」则需要进行合并父子结点和亲兄弟结点，使其变成非「2-结点」。
   // 左子结点是黑结点、左孙结点也是黑结点，说明左子结点是个「2-结点」
   if (!isRed(h.left) && !isRed(h.left.left)) {
     // 此时经过处理，左子结点则不是「2-结点」
     h = moveRedLeft(h);
   }
   // 左子结点不是「2-结点」，继续向下查看左子结点
   h.left = deleteMin(h.left);
   return balance(h);
 }
 
 // 当左子结点是「2-结点」时，将「2-结点」的左子结点转换成一个「3-结点」或者「4-结点」
 // Assuming that h is red and both h.left and h.left.left
 // are black, make h.left or one of its children red.
 private Node moveRedLeft(Node h) {
   assert (h != null);
   assert isRed(h) && !isRed(h.left) && !isRed(h.left.left);
   //
   flipColors(h);
   // 因为这是一颗左倾红黑树，当前结点为h，当前结点的右子节点的左子节点是红色，则说明当前结点的左子结点的亲兄弟结点是「3-结点」
   if (isRed(h.right.left)) {
     // 进行左旋转：亲兄弟的最小键转给父结点，父结点的最小键转给左子结点形成一个「3-结点」
     h.right = rotateRight(h.right);
     h = rotateLeft(h);
     flipColors(h);
   }
   // 左子结点的兄弟结点是「2-结点」
   return h;
 }
```

#### 删除最大键
删除最大键同样的道理，代码如下

1. 只需要沿着右链接向下进行变换，确保每一个途径的结点不是2-结点，到达底部后进行删除操作
2. 而确保不是2-结点的方式也是要么合并父亲和兄弟，要么向兄弟借（右旋转）

```java
public void deleteMax() {
   if(null == root) {
     return ;
   }
   if(!isRed(root.left) && !isRed(root.right)) {
     root.color = RED;
   }
   root = deleteMax(root);
   if(null != root) {
     root.color = BLACK;
   }
 }
 private Node deleteMax(Node h) {
   if(isRed(h.left)) {
     h = rotateRight(h);
   }
   if(h.right == null) {
     return null;
   }
   if(!isRed(h.right) && !isRed(h.right.left)) {
     h = moveRedRight(h);
   }
   h.right = deleteMax(h.right);
   return balance(h);
 }
```

#### 删除任意键
在普通的二叉查找树中，删除任意键的方法是T.Hibbard提出的用「后继结点」填充删除结点的位置，所谓「后继结点」，就是其右子树中最小的结点，用「后继结点」替换不会改变二叉查找树的性质。LLRB的删除任意键可以借鉴这个过程，先用「后继结点」替换，然后用deleteMin()删除右子树中最小的结点。

```java
/**
    * Removes the specified key and its associated value from this symbol table (if the key is in
    * this symbol table).
    *
    * @param key the key
    * @throws IllegalArgumentException if {@code key} is {@code null}
    */
   public void delete(Key key) {
     if (key == null) {
       throw new IllegalArgumentException("argument to delete() is null");
     }
     if (!contains(key)) {
       return;
     }
 
     // if both children of root are black, set root to red
     if (!isRed(root.left) && !isRed(root.right)) {
       root.color = RED;
     }
 
     root = delete(root, key);
     if (!isEmpty()) {
       root.color = BLACK;
     }
     // assert check();
   }
 
 // delete the key-value pair with the given key rooted at h
   private Node delete(Node h, Key key) {
     assert get(h, key) != null;
 
     int cmp = key.compareTo(h.key);
     if (key.compareTo(h.key) < 0) {
       if (!isRed(h.left) && !isRed(h.left.left)) {
         h = moveRedLeft(h);
       }
       h.left = delete(h.left, key);
     } else {
       if (isRed(h.left)) {
         h = rotateRight(h);
       }
       if (key.compareTo(h.key) == 0 && (h.right == null)) {
         return null;
       }
       if (!isRed(h.right) && !isRed(h.right.left)) {
         h = moveRedRight(h);
       }
       if (key.compareTo(h.key) == 0) {
         Node x = min(h.right);
         h.key = x.key;
         h.val = x.val;
         // h.val = get(h.right, min(h.right).key);
         // h.key = min(h.right).key;
         h.right = deleteMin(h.right);
       } else {
         h.right = delete(h.right, key);
       }
     }
     return balance(h);
   }
```
